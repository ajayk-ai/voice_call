PO Agent: Technical Documentation

For developers and operators · Updated 20 Oct 2026

PO Agent is one FastAPI process plus a sheet-sync process. It reads overdue PO lines from a Google Sheet mirrored into PostgreSQL, and escalates them by WhatsApp (UltraMsg), an AI voice call (FreJun + Gemini Live) and a Google Meet invite.

System overview and architecture

The scheduler inside the web app starts each daily run. Scenario 3 calls go through the voice agent's /flow and /media endpoints, which can run on a different server (Render) from the one placing the call.

The system has three parts:

  • Voice agent (backend/voice_agent): places calls through FreJun and bridges call audio to Gemini Live. A browser mode talks to Gemini over a WebSocket without a phone.
  • PO follow-up (backend/po_followup): the daily escalation engine, admin page, business dashboard and WhatsApp reply webhook.
  • Sheet sync (backend/po_sync): mirrors the Google Sheet into PostgreSQL every 60 s.

Production and Test are separate PostgreSQL databases (pending_po, pending_po_test) with the same schema.

Tech stack and project structure

The whole system is one Python 3.14 package served by FastAPI, plus a separate sheet-sync process. The frontend is plain HTML/CSS with no build step.

Core components and flows

Daily follow-up run

A run is DailyRun.execute() in services/run.py. The scheduler thread in services/followup.py ticks every 15 s and starts a run per environment when it is due.

  1. Take the per-environment PostgreSQL advisory lock (pg_try_advisory_lock). If another process holds it, the run is skipped.
  2. Optionally pull the latest Google Sheet into production (sync_sheet_to_prod).
  3. Read Alert_Log (today's rows), Line_Tracker, Phone_Master and Master. If Master cannot be read, log SHEETS_READ_FAILED and stop.
  4. Record this period's overdue check in followup.overdue_checks and followup.overdue_snapshot (skipped in preview).
  5. Compute each line's streak from the last checks (domain/overdue.py) and map it to a level: 1, 2, 3 or meeting.
  6. Mark lines no longer overdue as CLEARED in Line_Tracker.
  7. Build vendor/level groups (domain/escalation.py), apply Phone_Master numbers, and drop groups whose dedupe key is already in today's log or that are outside the vendor selection.
  8. For each group: send WhatsApp via UltraMsg, add a Call_Tasks row and place the agent call (Scenario 3), or add a Meeting_Tasks row and a Google Meet invite (meeting). Flush Alert_Log after every vendor.
  9. Save the run report in followup.runs. On failure, log WORKFLOW_ERROR, alert FOLLOWUP_ALERT_MOBILE, and retry up to 3 times, 10 minutes apart.

Phone call (Scenario 3 or Normal call)

  1. create_call() asks FreJun to ring the number. The flow URL carries a signed ticket and, for vendor calls, a ctx token.
  2. When the call is answered, FreJun posts to /flow. The server replies with a stream action pointing at wss://<host>/media, 16 kHz audio, chunk size 500.
  3. /media checks the ticket, decodes ctx into the vendor prompt and greeting, and opens a Gemini Live session.
  4. Two coroutines run side by side (run_bridge):
    • Caller → Gemini: base64 PCM16 16 kHz from FreJun goes straight into send_realtime_input.
    • Gemini → caller: 24 kHz PCM16 is filtered and downsampled to 8 kHz, buffered into whole 20 ms packets (320 bytes), and sent as audio messages.
  5. On barge-in (interrupted), pending audio is dropped and a clear message empties FreJun's queue.
  6. The session ends when either side closes or after MAX_SESSION_SECONDS (900 s). Turns, latency and interruptions are traced.

Call tokens

call_context.py lets one server place a call and another stream it (for example, the office PC places it and Render streams it).

  • ticket: issue time plus an HMAC keyed on TELER_API_KEY. /media refuses streams without a valid ticket younger than 1 hour (5 minutes of clock skew allowed). This stops anyone running Gemini sessions on our key.
  • ctx: vendor name, code and up to 10 PO lines, zlib-compressed, base64url-encoded and HMAC-signed. Max 4,000 characters, valid for 1 hour.

Both servers must share the same TELER_API_KEY.

Sheet sync

backend.po_sync mirrors every tab of the Google Sheet into schema sheets of pending_po every 60 s. Each tab becomes one table: cleaned column names, all TEXT, plus sheet_row. Only changed tabs are rewritten, each in one transaction. public.sync_state records rows, last sync and last error per tab.

Running locally, testing and deployment

Local development

Requirements: Python 3.14, PostgreSQL 15+, and uv (recommended).

uv sync --all-extras                                   # or: pip install -r requirements.txt "psycopg[binary]>=3.2" pytest
copy .env.example .env                                 # fill PO_DB_PASSWORD, GOOGLE_DELEGATED_USER; add service.json
.venv\Scripts\python -m backend.po_sync --once                  # Google Sheet -> pending_po
.venv\Scripts\python -m backend.po_followup copy-prod-to-test   # production -> pending_po_test
.venv\Scripts\uvicorn main:app --port 5050 --reload

Then open http://localhost:5050/dashboard, /admin, / and /docs. Set FOLLOWUP_SCHEDULER=false to keep the scheduler out of a dev server.

Phone calls need FreJun to reach your machine over HTTPS. Start a tunnel (cloudflared tunnel --url http://localhost:5050 or ngrok http 5050), put its URL in PUBLIC_URL, restart, then run python scripts/make_call.py. The browser voice agent needs no tunnel.

Tests and lint

.venv\Scripts\python -m pytest -q     # never touches PostgreSQL, Google, WhatsApp or FreJun
uvx ruff check .

CI (.github/workflows/ci.yml) runs uv sync --locked --all-extras, ruff and pytest on every push to main and every pull request.

Production option A: one Linux server (recommended)

One VM (2 vCPU / 4 GB) runs PostgreSQL, the sheet sync and the web app behind Caddy for HTTPS.

  1. Install PostgreSQL, Caddy, Python 3.14; clone to /opt/po-agent/app under user poagent; create .venv and install requirements plus psycopg[binary].
  2. Put .env (chmod 600) and service.json in the app folder. Set PUBLIC_URL and both access codes.
  3. Create systemd units po-agent (uvicorn main:app --host 127.0.0.1 --port 5050 --proxy-headers) and po-sync (python -m backend.po_sync), then enable them.
  4. Point Caddy at 127.0.0.1:5050. It handles certificates and WebSockets.
  5. Run po_sync --once and copy-prod-to-test, check /health, then do a Preview run in the admin page.

Run one web process (no --workers): WebSocket bridges and the rate limiter live in memory. Schedule a nightly pg_dump of pending_po; follow-up state exists only there. Logs: journalctl -u po-agent -f.

To deploy a new version: git pull, reinstall requirements, systemctl restart po-agent po-sync. Tables and columns are created on start, so there are no manual migrations.

  • UltraMsg works: a live Test-environment vendor test reaches your phone
  • SCM_HOD_MOBILE, SCM_HEAD_EMAIL and Phone_Master scenario numbers filled
  • /health answers over HTTPS at PUBLIC_URL
  • FOLLOWUP_ALERT_MOBILE set
  • UltraMsg webhook set to /webhooks/ultramsg?secret=… with message received on
  • Old n8n workflow switched off
  • A few days of automatic dry runs checked before switching to live
  • Database backups scheduled

Known limitations

  • Single web process. WebSocket audio bridges and the call rate limiter are in memory, so the app runs as one Uvicorn process. Runs are still safe across processes thanks to the advisory lock.
  • Scheduler depends on uptime. In option B the scheduler runs only while the office PC is on. A missed day neither counts nor breaks streaks, but no messages go out.
  • Render free plan sleeps. The first call after idle can fail with "Failed to fetch call flow" until the service wakes.
  • Call script size. The ctx token carries at most 10 PO lines (worst first) and 4,000 characters, so the agent does not read every line for large vendors.
  • Call outcomes are not parsed. The agent asks for dispatch status and dates, but answers stay in the transcript and traces; nothing writes them back to the sheet.
  • Vendor replies are stored raw. WhatsApp replies go to Vendor_Replies without interpretation; a PO number is filled only when written explicitly.
  • Restarts mid-run. A restart during a run marks it failed; the next automatic attempt retries it. Alert_Log is flushed per vendor, so nothing is sent twice.
